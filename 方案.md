Stage C 事件草稿重复冲突：问题分析与简化方案

1. 结论先说

问题不只是「模型偶发分错组」，而是 Stage C 把「聚合决策」和「持久化状态机」绑在一起了：

• 模型多轮改 已落库 的草稿成员；
• 本地用 过严且混合的精确身份 做硬校验；
• 校验失败会 整次 Stage C 失败，而不是降级成可审事件。

在不削弱「聚合 → 历史比对 → 争议核验 → 事件池」能力的前提下，正确方向是：

模型只产出完整事件分组方案；本地一次性校验 + 冲突消解 + 原子落库。
精确身份只做「强信号建议合并」，不做「跨草稿硬阻断」。

───

2. 现状：Stage C 实际在做什么

当前 Stage C（event_cluster_job.py + stage_c_agent）是一个多轮 tool agent：

list/search/read 候选
  → save_event_drafts（1–8 条，立刻 upsert 到 DB）
  → search_web / attach_evidence（按草稿）
  → 再 save / mark_unresolved / 再改成员
  → finalize_event_drafts（硬校验）
  → materialize → IntelEvent

本地硬能力其实是清楚的：

├────────────────────────────────────────┼────────────┼────────────────────────────────────────┤

├────────────────────────────────────────┼────────────┼────────────────────────────────────────┤

业务能力没问题；复杂混乱的是工作台状态模型，不是「要不要聚合/核验」。

3. 三类失败如何叠在一起

3.1 模型误归组 → 修正路径本身制造冲突

典型路径（文档里的 Claude Code / Transformers）：

1. 模型把 item A 写进草稿 X；
2. 发现错了，再 save_event_drafts 把 A 挪到 Y，或生成 unresolved-*；
3. 中间态可能短暂「A 仍在 X 缓存里 + 又在 Y」；
4. 若只修正部分草稿、旧草稿未清空成员，finalize 报 item N appears in more than one draft。

upsert_agent_draft(..., allow_member_reassignment=True) 会从旧草稿删成员，空草稿甚至会删掉；但：

• 校验读的是 draft.members 关系；
• session 配置是 expire_on_commit=False；
• 成员变更后 没有统一 expire/refresh；
• 于是「DB 已对、ORM 仍旧」可以复现「已调整仍报重复」。

这是 状态一致性 bug，不是聚合语义 bug。

3.2 精确身份规则把「同仓不同 Release」判成同一身份

def exact_identity_keys(value: Any) -> tuple[str, ...]:
    values = _mapping(value)
    url = canonical_event_url(values.get("canonical_url") or values.get("url") or values.get("source_url"))
    external_id = _normalize_external_id(values.get("external_id") or values.get("guid"))
    values = [value for value in (f"url:{url}" if url else None, f"external:{external_id}" if external_id else None) if value]
    return tuple(dict.fromkeys(values))

问题链：

1. GitHub 仓库 item：external_id=github_repo:...，canonical_url=https://github.com/owner/repo
2. GitHub Release item：external_id=github_release:<id>，但 collector 未设独立 release URL 时，落库会把 url 收成 canonical_url
3. 若多条 Release 的 url/canonical_url 都落到 仓库主页（或归一化后相同），则共享 url:https://github.com/owner/repo
4. finalize 要求：同一 exact identity 的 active 不能拆到两个草稿 → 不同 tag 的 Release 被硬捆或整批失败

这与产品语义相反：

• 同仓不同 Release = 不同版本事件，允许（且常应）拆分，并可用 split_reason=different_model_or_major_version
• 同 URL 转载/镜像 = 才应视为 duplicate 身份

另外，identity 校验对 所有 draft members 生效（含 rejected），所以「已拒绝审计草稿」也可因共享 URL 卡死整次 finalize。这是 故障放大。

3.3 失败模式是「全有或全无」

finalize / materialize 任一硬错误 → StageCAgentContractError → Stage C 失败 → D/Export 不跑。

对比 Stage D 已有的「校验失败 → 带错误重试完整 JSON」，Stage C 缺少：

• 本地自动消解（合并明显 duplicate、未覆盖 → unresolved singleton）；
• 或「返回完整方案再一次提交」的协议。

模型被推去 多轮修持久化状态，越修越乱。

文档里的三点（误归组、身份过严、ORM 未刷新）都对，但更完整的根因是：

L2 让错误可累积，L3 让错误不可恢复，L1 被误伤。

5. 设计原则（保能力、降混乱）

6. 单一写入点：一次 run 只接受一份完整 grouping plan，再原子落库。
7. 本地拥有不变量：item 唯一归属、active 覆盖、schema/guard —— 不靠模型自觉。
8. 身份是建议不是死刑：精确 duplicate → 自动并入同一事件包；语义相关但非 duplicate → 模型决定；冲突无法消解 → needs_review，不整批失败。
9. rejected 不阻断候选池：审计草稿可并存，但不参与「跨草稿 identity 硬冲突」。
10. 核验仍按事件：Tavily 绑定的是 plan 里的 event_key/claim，不是「半成品 DB 行」。
11. 可恢复：预算耗尽 / 模型未完成 → 未覆盖 active 自动 singleton needs_review（已有雏形，应成为主路径而非仅 budget 分支）。

6.2 模型输出契约（保留现有字段语义）

每个事件仍使用现有事件包字段（与 v12+ 一致，避免再发明分类学）：

• event_key（原 draft_key）
• event_family_key, item_ids, title, summary_cn, topic
• facts[], history_status, prior_event_key
• publishability, split_reason, caveats
• 可选：evidence_refs[]（本 session 已 attach 的 result_id）

约束：

• 一次 submit 必须覆盖全部 active（或显式 unresolved 段）；
• 允许 1 次「校验错误 + 压缩 plan 回传」修复（对齐 Stage D）；
• 禁止 再暴露「部分 save 已持久化成员」给模型当工作记忆。

6.3 本地 Committer 规则（核心）

A. 成员唯一

• 同一 item_id 出现在多个 event → 自动保留「更完整 / 更高 publishability / 先出现」之一，其余去掉；若无法判定 → 该 item 进 needs_review singleton，并打 caveat。

B. 精确身份（重写，不再双键一律硬杀）

┌───────────────────────────────────────────────────────────────────────────────────────┬──────────────┬─────────────────────────────┐
│ 信号                                                                                  │ 含义         │ 动作                        │
├───────────────────────────────────────────────────────────────────────────────────────┼──────────────┼─────────────────────────────┤
│ 相同 external_id（含 github_release:*）                                               │ 同一发布物   │ 强制同一事件                │
├───────────────────────────────────────────────────────────────────────────────────────┼──────────────┼─────────────────────────────┤
│ 相同 文章级 canonical URL（非仓库根、非列表页）                                       │ 同一文档镜像 │ 强制同一事件                │
├───────────────────────────────────────────────────────────────────────────────────────┼──────────────┼─────────────────────────────┤
│ 仅相同 GitHub 仓库根 URL，external 为不同 github_release:* 或 github_repo: vs release │ 同仓不同对象 │ 不强制合并；可作 soft hint  │
├───────────────────────────────────────────────────────────────────────────────────────┼──────────────┼─────────────────────────────┤
│ 相同 github_repo: external                                                            │ 同一仓库卡片 │ 强制同一事件                │
├───────────────────────────────────────────────────────────────────────────────────────┼──────────────┼─────────────────────────────┤
│ 无强身份，仅关键词/实体相近                                                           │ 语义聚合     │ 交给模型；family/split 约束 │
└───────────────────────────────────────────────────────────────────────────────────────┴──────────────┴─────────────────────────────┘

实现要点：

exact_identity_keys:
  - 若 external_id 匹配 github_release:* → 只返回 external:...（URL 不参与 exact）
  - 若 URL 是 GitHub 仓库根且 external 是 release/repo 混用 → URL 降为 related_hint，不进 exact set
  - 普通文章 URL 仍作为 exact

C. identity 冲突作用域

• 仅对 publishability in {candidate, needs_review} 做「必须可解释」检查；
• rejected 可与候选共享 URL/external 审计并存，不阻断 finalize；
• materialize 时 rejected 仍入库审计。

D. 未覆盖 / 预算耗尽

• 一律 _save_unresolved_draft 路径，标记 reason，needs_review 进 D；
• 不再因「模型没把状态修干净」导致 C 失败（除非 plan schema 彻底不可解析且修复耗尽）。

E. ORM

• committer 只写一次：先 delete session drafts，再 bulk insert；
• 或写后 session.expire_all() / 按 draft_id refresh members 再 validate；
• 校验只信「刚写入的 plan 结构」或「fresh query」，不信旧 relationship 缓存。

7. 分阶段落地

Phase 0 — 止血（小改，行为对齐文档）

1. 重写 exact_identity_keys（release / repo-root 特例）。
2. upsert_agent_draft 结束后 expire draft.members；list_agent_drafts 前可 populate_existing 或 expire_all。
3. _validate_agent_drafts：identity 硬冲突仅看 publishable drafts；或对 identity 冲突改为 自动 merge 建议错误信息 而非只报错。
4. 单测：
   • 两 release 同仓不同 external → 允许分草稿；
   • 同 external → 禁止分草稿；
   • 成员从 A 挪到 B 后 finalize 不报重复；
   • rejected 与 candidate 共享 URL 不失败。

Phase 1 — 协议简化（推荐主方案）

1. 新增 submit_event_plan：一次提交全部 events。
2. 本地 commit_event_plan()：校验 → 归一 → 原子替换 drafts → materialize。
3. 校验失败：返回 structured errors + 要求重提完整 plan（最多 N 次）。
4. 废弃热路径上的持久化 save_event_drafts（可暂时保留 dry-run 兼容）。
5. Prompt 改为「先完整分组，再按需搜索，最后一次提交」。

Phase 2 — 可选增强（非必须）

• 本地 soft clustering 预分组（同 external / 同强 URL / 同实体+24h）作为 只读 hint 塞进 initial_context，减少模型漏合。
• 不引入向量库/工作流引擎；hint 用现有字段即可。

9. 风险与边界

• 一次提交 token 变大：可用「先输出 event_key+item_ids 骨架，校验过后再补 title/facts」两拍提交；仍比多轮 save 干净。
• resume/断点：今天靠 DB drafts 续跑；简化后应靠 agent transcript + 最后成功 plan 快照。force/fingerprint 变更仍 reset。
• 自动 merge 过猛：只对 exact 强身份自动合并；语义合并仍归模型，避免又变回规则引擎选稿。
• GitHub 特例要写死测试：release URL、repo URL、repo card、trending 四类 fixture。
